# Ledger

Ledger — сервис учёта расходов на Go с PostgreSQL-репозиториями. Его интерфейс
использует Gateway на порту 8080; отдельный HTTP Ledger на порту 8081 также
предоставляет отчёт по интервалу с Redis-кэшем на 30 секунд.
При запуске демонстрационные данные и `budgets.json` не загружаются.

## Слои и сборка

- `domain/` — `Budget`, `Transaction`, их `Validate()`, ошибки и контракты
  бюджетов, расходов, атомарной операции категории, отчёта и кэша.
- `service/` — `Service` для бюджетов/расходов и `ReportingService` для отчёта.
  Реализация валидирует сущности и проверяет накопительный бюджет через
  доменные интерфейсы; зависимости от SQL, pgx и Redis отсутствуют.
- `internal/repository/pg/` — SQL-запросы, преобразование результатов и реализация
  `UnitOfWork` через SQL-транзакцию и блокировку категории. Правило бюджета
  остаётся в сервисе; обновление бюджета и добавление расхода используют ту же блокировку.
- `internal/cache/` — подключение Redis и реализация доменного контракта кэша.
- `internal/db/` — чтение `DATABASE_URL`/`DB_*`, открытие пула и `PingContext`.
- `app/` — сборка зависимостей, проверка подключения и схемы, освобождение ресурсов.
- `internal/httpapi/` и `cmd/ledger/` — HTTP-представления и запуск отдельного Ledger.
- `internal/integration/` — сценарии с настоящими PostgreSQL, Redis и миграциями.
- `ledger.go` — прежнее хранилище в памяти, сохранённое для совместимости API и тестов.

Сервис зависит от домена; репозитории и кэш реализуют его контракты; фабрика
знает конкретные реализации и передаёт их сервису. `domain`, `service`, `app`
публичны, поскольку Gateway — отдельный Go-модуль и не может импортировать
`ledger/internal/*`. Производственный код Gateway использует только `service` и `app`.

`app.New(ctx)` возвращает `(service.Service, closeFn, err)` и подключает только
PostgreSQL. Gateway после успеха выполняет `defer closeFn()` и передаёт сервис
в `api.NewHandler`. `app.NewReporting(ctx)` дополнительно подключает Redis
и возвращает `service.ReportingService` для отдельного HTTP Ledger.
Обе фабрики передают контекст в проверку подключения, освобождают уже открытые
ресурсы при ошибке и не запускают миграции. Ошибки логируются в `main` и приводят
к завершению с ненулевым кодом; при остановке приложения вызывают `closeFn`.

## Запуск

Из корня репозитория установите Goose, создайте БД и примените миграции:

```sh
go install github.com/pressly/goose/v3/cmd/goose@v3.21.1
export PATH="$(go env GOPATH)/bin:$PATH"
docker compose up -d --wait
export DATABASE_URL='postgres://postgres:postgres@localhost:5432/cashapp?sslmode=disable'
export REDIS_ADDR='localhost:6379'
export REDIS_DB='0'
export REDIS_PASSWORD=''
goose -dir ./ledger/migrations postgres "$DATABASE_URL" up
cd ledger
go run ./cmd/ledger
```

Compose создаёт `cashapp` при первом запуске PostgreSQL с пустым томом.
Успешные подключения к PostgreSQL и Redis выводятся в лог. Если `Ping` любого
сервиса не прошёл, Ledger завершает запуск с ошибкой. По умолчанию HTTP слушает
`:8081`; адрес меняется через `LEDGER_ADDR`.

`DATABASE_URL` имеет приоритет. Без него DSN собирается из `DB_HOST=localhost`,
`DB_PORT=5432`, `DB_USER=postgres`, `DB_PASS=postgres`, `DB_NAME=cashapp`
с `sslmode=disable`. Значения Redis по умолчанию: `REDIS_ADDR=localhost:6379`,
`REDIS_DB=0`, `REDIS_PASSWORD` пустой. Локальный Compose не задаёт пароль Redis;
переменная клиента применяется при подключении к серверу с авторизацией.
Пул PostgreSQL: 10 открытых, 5 простаивающих соединений, время жизни 5 минут.

Миграции 1–2 создают таблицы и индекс, миграция
`00003_gateway_compatibility.sql` меняет денежные поля на `NUMERIC` без заданных
точности и масштаба, дату — на `TEXT`. Благодаря этому Gateway сохраняет
положительные конечные `float64` без округления и любые строковые даты,
включая пустую. Существующие даты переходят в текст `YYYY-MM-DD`.
Секции `Up`/`Down` находятся в одном файле. Миграции применяются явно перед запуском.
Репозиторий обратимо экранирует NUL и обратные слеши внутри текстовых столбцов;
миграция сохраняет существующие строковые значения, HTTP получает исходный текст.
Фабрика проверяет не только наличие таблиц, но и совместимость типов миграции 3.
Откат последней миграции из корня:

```sh
goose -dir ./ledger/migrations postgres "$DATABASE_URL" down
```

Откат миграции 3 отказывается менять схему, если значение нельзя вернуть
в `NUMERIC(14,2)` или `DATE` без потери данных, либо текст содержит NUL. `down-to 0` откатывает все три
миграции и удаляет таблицы и данные; перед следующим запуском повторите `up`.

## HTTP-проверка

Для новой базы выполните по порядку:

```sh
curl -i -X POST http://localhost:8081/api/budgets \
  -H 'Content-Type: application/json' -d '{"category":"еда","limit":500}'
curl -i -X POST http://localhost:8081/api/transactions \
  -H 'Content-Type: application/json' \
  -d '{"amount":450,"category":"еда","description":"ланч","date":"2026-11-06"}'
curl -i -X POST http://localhost:8081/api/transactions \
  -H 'Content-Type: application/json' \
  -d '{"amount":100,"category":"еда","date":"2026-11-06"}'
curl -i http://localhost:8081/api/budgets
curl -i http://localhost:8081/api/transactions
curl -i 'http://localhost:8081/api/reports/summary?from=2026-11-01&to=2026-11-30'
curl -i 'http://localhost:8081/api/reports/summary?from=2026-11-01&to=2026-11-30'
```

Первые два POST дают `201`; превышение — `409` без вставки. GET читают данные
из БД. При перезапуске Ledger с тем же DSN данные сохраняются. Бюджет обновляется
через UPSERT по категории; при отсутствии бюджета расходы разрешены.
В отдельном HTTP Ledger сервис `NewStrict` сохраняет прежнюю валидацию:
дата расхода обязательна (`YYYY-MM-DD`), суммы положительные, до двух десятичных
знаков и не более `999999999999.99`. Транзакции возвращаются по `date DESC, id DESC`,
бюджеты — по категории.

Первый запрос отчёта при пустом кэше пишет `cache miss` в лог, следующий
в течение 30 секунд — `cache hit`. Ключ:
`report:summary:2026-11-01:2026-11-30`, значение — JSON. После добавления расхода
отчёт может отставать на время оставшегося TTL. Ошибка Redis во время работы
логируется; отчёт вычисляется через PostgreSQL. Списки бюджетов не кэшируются.

Gateway вызывает тот же слой сервиса внутри своего процесса и использует ту же
БД при одинаковом DSN. Его вариант `service.New` сохраняет прежнее поведение:
необязательные `description`/`date`, произвольную строковую дату, любые положительные
конечные суммы и порядок добавления расходов (`id ASC`). Для обоих приложений
бюджет учитывает всю историю категории, точное равенство лимиту допустимо.
ID назначает БД, пропуски в последовательности возможны.

Отчёт учитывает обе границы интервала и только записи с корректной датой
`YYYY-MM-DD`. Расходы Gateway без даты или с некорректной/произвольной датой
в отчёт по датам не входят, но продолжают учитываться в бюджете. Маршрута отчёта
в Gateway нет; Redis для его запуска не требуется.

[Общая инструкция](../README.md) содержит проверку SQL, TTL, конфигурацию портов
и интеграционных тестов. В каталоге `ledger/` обычные проверки запускаются так:

```sh
go test ./...
go vet ./...
```

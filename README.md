# Gateway и Ledger

Учебный проект: HTTP-шлюз и учёт расходов с бюджетами по категориям на Go 1.22
или новее. Gateway напрямую вызывает методы Ledger; хранилище работает в памяти
процесса Gateway. Оба модуля имеют собственный `go.mod`, внешних библиотек нет.
Команды ниже выполняются из корня репозитория.

## Структура

- `gateway/` — запуск HTTP-сервера на порту 8080.
- `gateway/internal/api/` — DTO, преобразования, маршруты, обработчики, middleware и HTTP-тесты.
- `ledger/` — импортируемый пакет: транзакции и бюджеты в памяти, валидация, загрузка JSON и тесты.
- `ledger/cmd/ledger/` — отдельная консольная демонстрация и её тесты.
- `ledger/budgets.json` — начальные бюджеты демонстрации.
- [AGENTS.md](AGENTS.md) и `rules/` — правила разработки.

## Запуск Gateway

В первом терминале:

```sh
cd gateway
go run .
```

Сервис продолжает работать до остановки через `Ctrl+C`.
Отдельно запускать Ledger для API не нужно. В `gateway/go.mod` настроен локальный импорт:

```go
require github.com/skitchen1992/Ledger/ledger v0.0.0

replace github.com/skitchen1992/Ledger/ledger => ../ledger
```

Каждый запуск Gateway начинает с пустых бюджетов и транзакций. При остановке
данные теряются; `ledger/budgets.json` используется только консольной демонстрацией.
Параллельные HTTP-запросы обращаются к одному экземпляру Ledger через mutex.

В другом терминале отправьте запрос:

```sh
curl -i http://localhost:8080/ping
```

Ожидается статус `HTTP/1.1 200 OK` и JSON-строка `"pong"`.
Другие методы для `/ping` возвращают `405 Method Not Allowed` с `Allow: GET`,
неизвестные пути — `404 Not Found`.

## HTTP API

Все ответы имеют заголовок `Content-Type: application/json; charset=utf-8`.
Middleware пишет в консоль метод, путь и длительность каждого запроса,
включая запросы с ошибками.

| Метод | Путь | Результат |
| --- | --- | --- |
| `GET` | `/ping` | `200`, JSON-строка `"pong"` |
| `POST` | `/api/transactions` | Создать расход: `201`, сохранённая транзакция с ID |
| `GET` | `/api/transactions` | `200`, массив транзакций в порядке добавления |
| `POST` | `/api/budgets` | Создать или обновить бюджет категории: `201`, бюджет |
| `GET` | `/api/budgets` | `200`, массив бюджетов, отсортированный по категории |

При отсутствии данных списки возвращают `[]`. Другие методы для API возвращают
`405` с `Allow: GET, POST`; неизвестные пути — `404`. Пути задаются без завершающего `/`.

Тело POST — ровно один JSON-объект. У транзакции обязательны `amount` и `category`;
`description` и `date` — необязательные строки. У бюджета обязательны `category`
и `limit`. Категория не может быть пустой или пробельной, сумма и лимит —
строго положительные конечные числа. Формат даты не проверяется.
Неизвестные поля игнорируются; ID всегда назначает Ledger, начиная с 1.
HTTP DTO преобразуются в доменные модели перед вызовом `Validate()` и методов хранилища.

Ошибки имеют вид `{"error":"описание"}`:

- `400 Bad Request` — некорректный JSON или ошибка валидации, состояние не меняется.
- `409 Conflict` — `{"error":"budget exceeded"}`, расход превысил бы лимит категории.
- `500 Internal Server Error` — `{"error":"internal server error"}`; причина записывается в лог.

Примеры ниже выполняются последовательно после запуска пустого Gateway.
Создайте бюджет:

```sh
curl -i -X POST http://localhost:8080/api/budgets \
  -H 'Content-Type: application/json' \
  -d '{"category":"еда","limit":500}'
```

Ответ: `201 Created`, `{"category":"еда","limit":500}`.
Добавьте транзакцию:

```sh
curl -i -X POST http://localhost:8080/api/transactions \
  -H 'Content-Type: application/json' \
  -d '{"amount":450,"category":"еда","description":"ланч","date":"2025-09-10"}'
```

Ответ: `201 Created`:

```json
{"id":1,"amount":450,"category":"еда","description":"ланч","date":"2025-09-10"}
```

Получите оба списка:

```sh
curl -i http://localhost:8080/api/transactions
curl -i http://localhost:8080/api/budgets
```

Проверьте превышение бюджета — ответ `409`, транзакция не сохраняется:

```sh
curl -i -X POST http://localhost:8080/api/transactions \
  -H 'Content-Type: application/json' \
  -d '{"amount":100,"category":"еда","description":"кофе","date":"2025-09-10"}'
```

Обновите лимит — ответ `201`; предыдущие расходы сохранятся:

```sh
curl -i -X POST http://localhost:8080/api/budgets \
  -H 'Content-Type: application/json' \
  -d '{"category":"еда","limit":1000}'
```

Проверьте валидацию — ответ `400` с описанием ошибки суммы:

```sh
curl -i -X POST http://localhost:8080/api/transactions \
  -H 'Content-Type: application/json' \
  -d '{"amount":0,"category":"еда"}'
```

## Запуск Ledger

Во втором терминале из корня репозитория:

```sh
cd ledger
go run ./cmd/ledger
```

Запускайте Ledger из каталога `ledger/`: программа открывает `budgets.json`
относительно текущего рабочего каталога. Файл содержит начальные лимиты:

```json
[
  { "category": "еда", "limit": 5000 },
  { "category": "транспорт", "limit": 1000 }
]
```

`main` открывает файл через `os.Open`, передаёт `bufio.NewReader` в `LoadBudgets`
и закрывает файл после выполнения. `LoadBudgets` устанавливает проверенные
бюджеты через `SetBudget`. Это единственный источник начальных лимитов:
изменение файла меняет результат демонстрации.

После сообщения `Ledger service started` программа передаёт отдельные примеры
`Transaction` и `Budget` в `CheckValid` и выводит:

```text
Проверка ledger.Transaction: данные корректны
Проверка ledger.Budget: данные корректны
```

Эти примеры демонстрируют работу общего интерфейса и не добавляются в хранилище.
Затем при стандартном файле программа показывает пять добавленных транзакций
и один отказ с причиной `budget exceeded`.
Расходы на еду 1500 и 2000 рублей принимаются; следующие 2000 рублей
отклоняются, поскольку общая сумма стала бы 5500. Затем 1500 рублей принимаются:
итог ровно 5000 разрешён. Расходы на транспорт 700 рублей и книги 950 рублей
также принимаются. Для книг бюджет не задан.

Итоговая часть вывода:

```text
Сохранено транзакций: 5
1 | 1500.00 руб. | еда | Продукты | 2026-11-06
2 | 2000.00 руб. | еда | Покупки на неделю | 2026-11-06
3 | 1500.00 руб. | еда | Обед | 2026-11-06
4 | 700.00 руб. | транспорт | Проездной | 2026-11-06
5 | 950.00 руб. | книги | Учебник Go | 2026-11-06
```

Отклонённый «Ужин» не попадает в список и не расходует ID. Ledger выводит историю
через `ListTransactions`, затем завершает работу. Транзакции хранятся только
в памяти; каждый запуск начинает новую историю. Консольная демонстрация и Gateway
используют один доменный пакет, но каждый процесс создаёт собственное состояние.
Сетевого взаимодействия между ними нет.

## Валидация

Общий контракт проверки данных задаёт интерфейс:

```go
type Validatable interface {
	Validate() error
}

func CheckValid(v Validatable) error {
	return v.Validate()
}
```

`Transaction` и `Budget` реализуют этот интерфейс: их методы `Validate()`
возвращают `nil` для корректных данных или ошибку с описанием проблемы.
Категория не может быть пустой или состоять только из пробелов; сумма транзакции
и лимит бюджета должны быть положительными конечными числами. Ноль,
отрицательные значения, `NaN` и бесконечность отклоняются. Формат строкового
поля `Date` не проверяется. Методы валидации не логируют; ошибки обрабатывает
вызывающий код.

## Транзакции

`Transaction` содержит поля `ID int`, `Amount float64`, `Category string`,
`Description string`, `Date string`. Суммы заданы в рублях; в демонстрации даты
используют формат `YYYY-MM-DD` и хранятся как строки.

Хранилище — структура `Ledger` с собственным срезом `[]Transaction`.
Её нулевое значение также готово к использованию.

- `(*Ledger).AddTransaction(tx Transaction) error` сначала вызывает `tx.Validate()`.
  Некорректные данные отклоняются без изменения истории. Если бюджет задан,
  проверяется сумма всех принятых расходов категории вместе с новым. Превышение
  возвращает `ErrBudgetExceeded`, распознаваемую через `errors.Is`; при успехе — `nil`.
- Хранилище само назначает последовательные ID с 1, заменяя переданный ID.
  Отклонённая транзакция не расходует ID.
- `(*Ledger).ListTransactions() []Transaction` возвращает копию всех транзакций
  в порядке добавления. Изменение копии не затрагивает хранилище.

## Бюджеты и JSON

`Budget` содержит `Category string` и `Limit float64`. Бюджеты хранятся
в `map[string]Budget` по названию категории. Лимит фиксирован для всей истории
категории; периодов и автоматического сброса расходов нет.

`(*Ledger).SetBudget(b Budget) error` вызывает `b.Validate()` перед добавлением
или заменой лимита. При ошибке состояние не меняется; при успехе возвращается
`nil`. Уже принятые расходы сохраняются и учитываются при следующем добавлении.
Если новый лимит меньше накопленных расходов, история остаётся, но новые расходы отклоняются.
Категория без бюджета не ограничена.

`(*Ledger).ListBudgets() []Budget` возвращает независимую копию бюджетов,
отсортированную по категории. Пустое хранилище возвращает пустой срез.

Поля сумм остаются `float64`. Для проверки лимита их кратчайшие десятичные
представления складываются точно через стандартный `math/big.Rat`: расходы
`0.10` и `0.20` принимаются при лимите `0.30`. Произвольного допуска на превышение
нет. Точность, уже потерянная до передачи значения в `float64`, не восстанавливается.

`(*Ledger).LoadBudgets(r io.Reader) error` принимает ровно один JSON-массив:

- `category` и `limit` обязательны. Пустая или пробельная категория, нулевой
  или отрицательный лимит, пропущенный `limit` и `null` вместо него считаются ошибкой.
- Сначала проверяются весь массив и конец документа, затем бюджеты применяются
  через `SetBudget`. Для значений используется `Budget.Validate()`.
  При ошибке бюджеты и транзакции остаются прежними.
- Повторная категория обновляет предыдущий лимит; последнее значение побеждает.
  Категории, отсутствующие в массиве, сохраняют существующие бюджеты.
- `[]` ничего не меняет. При запуске с пустым массивом бюджетов нет, поэтому
  все шесть демонстрационных транзакций принимаются.
- Ошибки чтения и разбора JSON возвращаются с контекстом и исходной причиной.
  `LoadBudgets` не закрывает переданный источник.

При ошибке открытия файла или загрузки Ledger сообщает причину и завершается
с ненулевым кодом, не запуская демонстрацию. Ошибки вывода также останавливают
выполнение. Ожидаемый отказ по бюджету выводится отдельно, после него обработка
остальных транзакций продолжается.

## Проверки

Из корня репозитория:

```sh
gofmt -l .
(cd gateway && go test ./... && go vet ./...)
(cd ledger && go test ./... && go vet ./...)
(cd gateway && go test -race ./...)
(cd ledger && go test -race ./...)
```

У `gofmt -l .` не должно быть вывода. Корневого `go.mod` нет, поэтому Go-проверки
выполняются отдельно в каждом модуле.

Для покрытия и HTML-отчётов:

```sh
(cd gateway && go test ./... -cover -coverprofile=cover.out && go tool cover -html=cover.out -o cover.html && go tool cover -func=cover.out)
(cd ledger && go test ./... -cover -coverprofile=cover.out && go tool cover -html=cover.out -o cover.html && go tool cover -func=cover.out)
```

Профили сохраняются в `gateway/cover.out` и `ledger/cover.out`, HTML-отчёты —
в `gateway/cover.html` и `ledger/cover.html`. HTML можно открыть в браузере;
эти файлы исключены из Git. Для вывода отдельных сценариев добавьте `-v`
к `go test`.

Покрытие тестами по сформированным профилям:

| Область | Покрытие операторов |
| --- | --- |
| Домен `ledger` | 97,3% |
| HTTP-пакет `gateway/internal/api` | 93,2% |
| Весь модуль `ledger`, включая CLI | 93,4% |
| Весь модуль `gateway`, включая запуск сервера | 88,9% |

Итоги модулей — строки `total` из `go tool cover -func=cover.out`.
Точки входа `main()` напрямую тестами не вызываются и учтены в этих итогах.

Тесты хранилища создают собственные экземпляры `Ledger` и регистрируют
`t.Cleanup(ledger.Reset)`. Метод `(*Ledger).Reset()` очищает транзакции и бюджеты;
следующая транзакция снова получает ID 1. Общего глобального хранилища нет.
Независимые unit-тесты и табличные подтесты используют `t.Parallel()`.
HTTP-сценарии выполняются последовательно с новым `api.NewHandler()` для каждого
независимого сценария. В `TestTransactionsAPI` ветки `ok`, `exceeded` и
`bad_json` проверяют цепочку создания бюджета и транзакций через настоящий роутер.

Тесты проверяют HTTP DTO, статусы и JSON ошибок, пустые списки, логирование,
параллельные запросы без превышения лимита и повторения ID,
валидацию через общий интерфейс, сохранение полей
и порядка транзакций, ID без пропусков при отказе, копию истории, суммарные лимиты
и точное равенство, независимость категорий, обновление бюджета,
загрузку JSON без частичных изменений,
ошибки чтения и парсинга, вывод демонстрации и ошибки записи. Файловые тесты
используют временные каталоги и не меняют рабочий `ledger/budgets.json`.
